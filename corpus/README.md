# The corpus run

Twenty to fifty generated applications, each with a shallow hand-written spec, run through
the tool, with every finding reviewed by hand and classified. It produces the number this
project has to be able to defend: how often a finding is wrong.

`06-TESTING.md` owns the procedure. `docs/plan/PROGRESS.md` tracks the tasks. This file is
the layout and the ground rules. **`RESULTS.md` is the result**: the rate, the per
application table, the aggregate, and the limits on the number.

## Ethics and scope

**Only applications the author owns or has explicit permission to inspect.** No third
party production systems, no reconnaissance of applications belonging to others, and no
publication of any finding tied to an identifiable third party application without
consent. The tool is pointed at consenting targets only.

**Every application in this corpus was generated for this purpose from the prompt set in
`prompts.md`.** That is the first of the three sources `06-TESTING.md` lists and the one
it prefers. The other two, open source projects that state they were AI generated and
applications built by classmates, both need a human to obtain consent or vouch for
provenance, so nothing enters this corpus by either route without that happening first.

**The credentials in these applications are fixture data and are written down on purpose.**
An `env.json` beside an application holds the tokens its config names. They belong to
nobody, they authenticate against nothing outside this repository, and a corpus that
needed real credentials would be a corpus nobody else could reproduce.

## What the number is worth, and what it is not

A corpus generated by a model shares that model's habits. A check that is blind to a
pattern will be blind to it on both sides, so the false positive rate this produces reads
better than one measured against applications written by strangers. The prompt set is
written to push against that, and the limitation is reported as part of the result rather
than as a footnote under it.

## Layout

Every corpus application is an ordinary qai project. Running the tool against one is
`qai check` in its directory and nothing else, because a corpus needing its own invocation
would be measuring the harness rather than the product.

```
corpus/
  README.md              this file
  prompts.md             the fixed prompt set every application came from
  run.ts                 the runner: every application, checked once, recorded
  lib/                   discovery and tabulation, tested like product code
  apps/
    <slug>/
      app/index.ts       an HTTP server that listens on process.env.PORT
      spec/<slug>.spec.yaml
      qai.config.yaml    baseUrl is http://127.0.0.1:47810
      env.json           optional, fixture credentials the config names
      NOTES.md           optional, which prompt produced this and what it is
  results/
    <stamp>/
      manifest.json      what ran, what did not, and why
      <slug>.run.json    the RunResult, one per application that checked
```

An application is started with `PORT` set and is expected to listen on it. One runs at a
time, on one fixed port, so there is no config rewriting and no race for a socket.

A directory under `apps/` that is missing any required part is **reported, not skipped**.
The number this stage produces is a fraction, and a denominator that quietly drops what it
could not read is a better number than the corpus earned.

## Running it

```
pnpm build
node --experimental-strip-types corpus/run.ts
```

The build is not optional: `packages/cli/bin/qai.js` runs `dist`, so a tool change that
has not been built is not a tool change the corpus will see.

The runner exits zero whenever the run itself completed. What was found is in the results,
and an application having findings is the expected and interesting case rather than a
failure of the run.
